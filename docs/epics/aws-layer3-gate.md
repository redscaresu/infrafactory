# Nothing an AWS model writes reaches a real apply unless one gate, parameterised by cloud, admits it, with per-type attribute allowlists, the exact user_data expression, the resolved AMI and the post-apply account and user-data checks wired into the Layer 3 path.

**Done when:**
- The gate takes the scenario's cloud at all four call sites (seams from aws-layer3-seal-and-dispatch) and admits the web_step_one HCL. It refuses, each with a fixture in internal/cli/layer3_hcl_shape_test.go: a second `provider "aws"` block; `alias`; a `provider =` meta-argument; `region` not equal to the configured region; any provider attribute other than region and s3_use_path_style, and any nested provider block other than infrafactory's default_tags with the run id (contradiction 4); required_providers source not exactly hashicorp/aws; any version other than the exact pin (the gate constant equals the pin fakeaws-step-one-surfaces chose); count and for_each; provisioner, connection, module, data; more than one aws_instance (the HLD requires exactly one); more than one aws_eip; aws_launch_template; a type outside the AWS allowlist.
- Per-type attribute allowlists replace a denylist, the layer3EnumBounds shape (layer3_hcl_shape.go:931): aws_instance admits ami (equal to the id resolved this run), instance_type (t3.micro, t3.small), subnet_id, vpc_security_group_ids, associate_public_ip_address, user_data, tags, root_block_device (volume_size <= 20, volume_type gp3, delete_on_termination absent or true) and refuses the rest, so tenancy, ebs_block_device, network_interface, iam_instance_profile, disable_api_termination = true, user_data_base64 and user_data_replace_on_change all fail with a fixture; aws_vpc refuses instance_tenancy = dedicated; aws_subnet and aws_eip get their own lists.
- user_data must be exactly file("${path.module}/infrafactory-user-data.sh"): file() is not on layer3PureFunctions (layer3_hcl_shape.go:770-860, contradiction 14), so the gate adds a single exact-AST exception, a FunctionCallExpr named file whose one argument is a TemplateExpr of [ScopeTraversalExpr path.module, literal "/infrafactory-user-data.sh"], recorded in ADR-0023; file("infrafactory-user-data.sh"), file("/proc/self/environ") and any other call are refused with fixtures. Before any tofu runs, the gate also requires that path to be a regular file byte-equal to the renderer's output for this run.
- The AWS allowlist (aws_vpc, aws_subnet, aws_internet_gateway, aws_route_table, aws_route, aws_route_table_association, aws_security_group, aws_instance, aws_eip) lands in internal/config/config.go:300, infrafactory.yaml:88 and docs/layer3-coverage.md together, partitioned per cloud: a scaleway_ type in an AWS stack and an aws_ type in a Scaleway stack are each refused with a fixture (today one flat list, config.go:300-314). The coverage doc's regex and title admit aws_ (internal/cli/layer3_coverage_doc_test.go:36-117, contradiction 6) and an aws-web-live row is 'runnable, unrun'; TestLayer3CoverageDoc*, TestLayer3DefaultAllowlistMatchesCheckedInConfig and aws-layer3-claim-sweep-reap's allowlist-to-collection mapping test pass with the new entries.
- A table test proves every allowlisted AWS type carries arn or owner_id in the pinned provider's schema or sits on the AWS child list (aws_eip especially); a type on neither is refused.
- Post-apply checks run on the Layer 3 path and a mismatch fails the run at test_command.go: every state resource with arn or owner_id carries the account preflight returned, children through their parent (helper from aws-layer3-seal-and-dispatch); the instance's API user data (DescribeInstanceAttribute userData, base64) equals the rendered file byte for byte, the state SHA1 is not compared. Both have fake-doer unit tests AND a test that the Layer 3 path calls them (a fake that fails the compare must fail the run).
- The Scaleway gate's behaviour is unchanged: every existing test in layer3_hcl_shape_test.go passes untouched; the provider label check (layer3_hcl_shape.go:280-283) and source constant (:497) become per-cloud.

**Out of scope:** The policy, scenario and holdout (aws-ingress-policy-and-holdout); the sweep and claim; fakeaws changes; step-two types; the CLI refusals (aws-layer3-seal-and-dispatch).
